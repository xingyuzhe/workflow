## Context

The current source layout stores canonical prompts under `.cursor/workflow/pack`, project rules under `.cursor/rules`, MCP definitions under `.cursor/mcp.json`, and duplicates metadata/state across Cursor and Codex directories. Codex assets are generated by parsing Cursor-specific formats.

## Goals / Non-Goals

**Goals:**

- Make shared workflow semantics independent from Cursor and Codex.
- Keep exactly one source of truth for packs, rules, MCP, metadata, and state.
- Generate deterministic client adapters and detect any drift.
- Preserve project-owned content outside managed regions.

**Non-Goals:**

- Preserve the old Cursor-owned source layout.
- Maintain importers, fallback readers, or dual-source behavior.
- Hide unsupported MCP or rule fields.

## Decisions

- Use `.workflow/` as the canonical root.
- Use JSON for structured canonical MCP and rule metadata because Windows PowerShell can parse it without adding a YAML runtime dependency; rule bodies remain Markdown.
- Store rule metadata in `.workflow/rules.json` and bodies under `.workflow/rules/`.
- Generate `.cursor/mcp.json`, `.cursor/rules/**/*.mdc`, `.agents/rules/**/*.md`, the Codex MCP managed block, Cursor commands/router, and Codex skill references.
- Store only `.workflow/version.json`, `.workflow/manifest.json`, and `.workflow/state.json`; client copies are derived runtime assets, not metadata authorities.
- Doctor compares generated expectations without writing. `-Fix` regenerates owned outputs and then runs the same strict checks.

## Risks / Trade-offs

- JSON is more verbose than YAML but avoids a new parser dependency and makes strict validation deterministic.
- Generated client files remain physically duplicated because clients require native layouts; ownership and drift checks prevent them becoming competing sources.
- Native-only MCP options require explicit client extension objects and adapter validation.
